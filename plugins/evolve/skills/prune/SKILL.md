# evolve:prune — remove vehicles, never traits

Prune is the third exclusion status and the only one about redundancy: a retraction says the measurement was wrong, a retirement says the mechanism is bad, a prune says the score stays TRUE and the candidate is a redundant vehicle — every trait it carries is held at-least-as-well by a diverse set of other live candidates, and every trait-PAIR by at least one carrier at-or-above it (pairs get the anchor, not the diversity bar — present the certificate as exactly that, no stronger). Pruned candidates leave selection (parents, crossover partners, inspirations, the board default) and nothing else: dedup, lineage, `evolve apply` and history are untouched, and reinstatement is one append with no re-measurement. The engine computes the plan; the owner decides. Never apply a plan the owner has not seen.

1. **Plan** — `evolve prune --plan` (registry mode; add `--min-carriers <D>` only if the owner names a bar — default 3, and the bar must be a positive integer). Always re-run the plan fresh: it is a pure function of the CURRENT archive, and any ingest since the last plan changes it. Genome-less candidates are unplannable (the plan warns); they can still be pruned explicitly via `--ids` if the owner directs — but say so when they are: an explicit genome-less prune has NO coverage certificate, so doctor can never audit it, and the ceremony's safety net does not cover it.
2. **Present** — pool / prunable / kept counts, the prunable ids with their fitness and weakest-link evidence (`min_trait_carriers`, `min_pair_carriers` — the margins, not a verdict), and every plan warning verbatim (unmeasured noise floor means the strictest margin; few axes weaken the diversity test). Note where the prunable set sits relative to the board's top. Then stop and wait for the owner's explicit approval — of the whole set or a subset. Do not editorialize which candidates "deserve" pruning; the numbers are the presentation.
3. **Apply** — `evolve prune --ids <approved,ids> --reason "<the owner's rationale>"`, passing the same `--min-carriers` the plan used (it is recorded on each record, and every future audit re-checks the prune at THAT bar). The batch is atomic — one refused id (unknown, already pruned, retracted, out of scope, or the rootless baseline) refuses the whole batch and names why. Surface any slots-file warnings: a pruned id that is a persisted parent/partner of an in-flight round makes that slot's re-brief path fail closed until the round completes or the id is reinstated — scoring and ingesting the slot's already-dispatched children is unaffected.
4. **Verify** — the verb already judges itself by effect (the status must register in the view, not just append). Confirm outward: `evolve board` shows the pruned count line (`--all` appends the pruned rows, marked), and `evolve doctor`'s `prune_coverage` check re-derives every standing certificate. The check FAILS only when a pruned candidate's trait or pair has been LOST from the pool entirely (zero surviving carriers — the invariant itself broken); mere thinning below the recorded bar is a warning for the owner to adjudicate. Report the numbers.
5. **Voided certificates and reinstatement** — when doctor warns that a standing prune no longer holds (a later retraction or re-score thinned its carriers), PRESENT the warning to the owner; the choice is theirs and it is two-way — reinstate (`evolve prune --id <id> --reinstate --reason "<why>"`, no re-measurement needed: the score was always valid) or accept the thinner coverage deliberately. Never reinstate on the warning alone: nothing in this system auto-reinstates — not a new score (deliberate: new data says nothing about redundancy), not a doctor warning, not this skill.

Standing rules of the status: the baseline is never pruned (the engine refuses — a re-measurement roster needs it); retraction outranks prune (a pruned-then-retracted id is handled by retraction's rules everywhere — reinstating its prune does NOT return it to selection, and the verb says so); a prune is scoped to the partition whose pool justified it (on an unpinned multi-env project the engine refuses ambiguous ids — pin `fitness.selection_env` first); if the owner's goal is to kill a MECHANISM rather than a redundant vehicle, that is retirement (`evolve/retired_impls.json`), not prune; pruned status must never reach inventor-facing text — the diet enforces this, so if a brief or jail build fails closed on a pruned parent, the remedy is resample-or-reinstate, said to the OWNER, never explained to an inventor.
